# 제품 요구사항 명세서 (PRD): Real-Time Chat Service
**버전: 2.2**

# Overview
본 문서는 Spring Boot WebFlux와 Kotlin 기반의 실시간 웹 채팅 서비스 개발 프로젝트를 정의합니다. 기존 메신저 서비스의 복잡성과 제약 없이, 개발자가 완전히 제어할 수 있는 단순하고 효율적인 실시간 채팅 플랫폼을 제공하는 것이 목표입니다.

이 서비스는 소셜 네트워킹과 실시간 소통에 익숙한 20-30대 사용자, 특히 개발자 커뮤니티와 소규모 팀 협업 환경을 대상으로 합니다. 데이터 특성에 맞는 효율적인 관리를 위해 사용자 정보는 PostgreSQL에, 대화 내용은 MongoDB에 분리 저장하여 고성능을 추구하는 현대적 아키텍처를 채택합니다.

핵심 가치는 지연 없는 실시간 양방향 소통과 완전한 개발자 제어권 제공입니다.

# Core Features

## 사용자 인증 (User Authentication)
- **What it does**: 이메일, 비밀번호, 닉네임을 사용한 회원가입/로그인 및 JWT 토큰 기반 인증 시스템
- **Why it's important**: 서비스 보안 유지 및 사용자별 활동 식별 기반을 제공하여 개인화된 채팅 경험 구현
- **How it works**: RESTful API 엔드포인트를 통한 인증 요청 처리, JWT 토큰 발급 및 검증으로 stateless 인증 구현

## 채팅방 관리 (Chat Room Management)
- **What it does**: 공개 채팅방 생성, 활성 채팅방 목록 조회, 채팅방 참여/퇴장 기능
- **Why it's important**: 주제별 소통 공간 제공 및 커뮤니티 형성 기반으로 사용자 참여도 향상
- **How it works**: RESTful API를 통한 채팅방 CRUD 작업 및 실시간 상태 동기화

## 실시간 메시징 (Real-Time Messaging)
- **What it does**: Reactive WebSocket Handler 기반 실시간 텍스트 메시지 송수신
- **Why it's important**: 서비스의 핵심 가치인 실시간 양방향 소통을 제공하여 즉각적인 상호작용 경험 구현
- **How it works**: WebFlux의 Reactive WebSocket API와 Redis Pub/Sub를 활용한 메시지 브로드캐스팅

## 대화 내용 영속성 (Message Persistence)
- **What it does**: 메시지 저장 및 채팅방 재입장 시 이전 대화 기록 제공
- **Why it's important**: 대화 맥락 유지 및 비동기적 소통 지원으로 사용자 편의성 극대화
- **How it works**: MongoDB 저장 및 페이지네이션 기반 메시지 히스토리 API

# User Experience

## User Personas
- **Primary Persona**: 소셜 미디어 및 메신저 앱에 익숙한 20-30대 기술 친화적 사용자
  - 빠른 응답을 기대하며 직관적인 인터페이스 선호
  - 다중 채팅방 참여 및 실시간 알림 필요
- **Secondary Persona**: 개발팀 내부 커뮤니케이션을 위한 개발자 그룹
  - 기술적 토론 및 코드 공유가 주요 사용 사례
  - 안정성과 확장성에 대한 높은 기대치

## Key User Flows
1. **신규 사용자 온보딩 플로우**
   - 회원가입 (이메일, 닉네임, 비밀번호) → 로그인 → 채팅방 목록 확인 → 첫 채팅방 참여 → 환영 메시지 수신

2. **일반 채팅 참여 플로우**
   - 채팅방 선택 → 입장 → 과거 메시지 로드 (최근 50개) → 실시간 채팅 참여 → 메시지 전송/수신

3. **채팅방 생성 플로우**
   - 생성 버튼 클릭 → 채팅방 정보 입력 (이름, 설명) → 생성 완료 → 자동 입장 → 첫 메시지 작성

## UI/UX Considerations
- **반응형 웹 디자인**: 데스크톱과 모바일 환경 모두에서 일관된 사용자 경험 제공
- **실시간 피드백**: 메시지 전송 상태(전송중/완료/실패), WebSocket 연결 상태 등을 즉시 시각적으로 표시
- **직관적 인터페이스**: 최소한의 학습 곡선으로 즉시 사용 가능한 간결한 UI 설계
- **성능 최적화**: 메시지 로딩 시 스켈레톤 UI, 무한 스크롤 기반 히스토리 로드

# Technical Architecture

## System Components
- **Web Framework**: Spring Boot 3.5.4 with WebFlux (이벤트 루프 기반 논블로킹 처리)
- **Programming Language**: Kotlin 2.2.10 (Coroutines 기반 비동기 처리)
- **Build Tool**: Gradle 9.0.0 with Kotlin DSL

## Data Models
```kotlin
// PostgreSQL (User & ChatRoom)
@Entity
data class User(
    @Id val id: Long,
    val email: String,
    val passwordHash: String,
    val nickname: String,
    val createdAt: LocalDateTime
)

@Entity
data class ChatRoom(
    @Id val id: Long,
    val name: String,
    val description: String?,
    val createdAt: LocalDateTime
)

// MongoDB (ChatMessage)
@Document
data class ChatMessage(
    @Id val id: String,
    val roomId: Long,
    val userId: Long,
    val content: String,
    val timestamp: LocalDateTime
)

// WebSocket Protocol
data class WebSocketMessage(
    val type: MessageType,
    val roomId: Long,
    val content: String,
    val userId: Long,
    val timestamp: LocalDateTime
)

enum class MessageType {
    CHAT, JOIN, LEAVE, TYPING
}
```

## APIs and Integrations
- **REST API Endpoints**:
  - `/api/auth/*` - 사용자 인증 (회원가입/로그인/토큰 갱신)
  - `/api/rooms/*` - 채팅방 관리 (생성/조회/참여/퇴장)
  - `/api/messages/*` - 메시지 히스토리 (조회/페이지네이션)

- **WebSocket Endpoints**:
  - `/chat` - 실시간 메시지 송수신 (Reactive WebSocket Handler)

- **Message Broadcasting**: Redis Pub/Sub 패턴으로 다중 서버 간 메시지 동기화

- **Security**: JWT 기반 인증, CORS 설정, XSS 방지

## Infrastructure Requirements
- **Application Layer**: Containerized Spring Boot WebFlux application
- **Database Layer**:
  - PostgreSQL 15+ (사용자/채팅방 메타데이터)
  - MongoDB 7+ (메시지 저장)
  - Redis 7+ (캐시/세션/Pub-Sub)
- **Load Balancing**: Nginx 또는 Spring Cloud Gateway (WebSocket Sticky Session 지원)
- **Monitoring**: Spring Boot Actuator, Micrometer, Prometheus

# Risks and Mitigations

## Technical Challenges
- **Risk**: WebFlux 기반 WebSocket 연결 관리 및 상태 동기화의 복잡성
- **Mitigation**: Kotlin Coroutines와 Reactive Streams를 적극 활용하여 비동기 처리 복잡도 감소, Redis 기반 분산 세션 관리로 상태 일관성 보장, 체계적인 WebSocket 연결 상태 모니터링 구현

## Figuring out the MVP that we can build upon
- **Risk**: STOMP 미지원으로 인한 메시지 라우팅 및 프로토콜 설계 복잡성
- **Mitigation**: 명확한 커스텀 JSON 메시지 프로토콜 정의, Redis Pub/Sub 채널 기반 단순한 라우팅 구조, 확장 가능한 메시지 타입 시스템 설계
- **Risk**: MVP 범위 비대화로 인한 개발 지연 및 핵심 기능 집중도 저하
- **Mitigation**: 엄격한 MVP 범위 준수 (인증 + 채팅방 + 실시간 메시징만), 핵심 기능 우선 구현 후 점진적 확장, 각 단계별 동작하는 데모 버전 확보

## Resource Constraints
- **Risk**: Reactive Programming (WebFlux, R2DBC, Reactive WebSocket) 학습 곡선 및 개발 생산성 저하
- **Mitigation**: Kotlin Coroutines 적극 활용으로 Reactive Streams 복잡도 감소, 체계적인 학습 계획 및 단계적 적용, 페어 프로그래밍과 코드 리뷰를 통한 지식 공유
- **Risk**: 다중 데이터베이스 (PostgreSQL, MongoDB, Redis) 운영 복잡성
- **Mitigation**: 각 데이터베이스별 명확한 역할 분담, 트랜잭션 경계 및 데이터 일관성 규칙 정의

# Appendix

## Research Findings
- **WebSocket vs Server-Sent Events**: WebSocket 선택 (양방향 통신 필요성 및 실시간 상호작용 요구사항)
- **Reactive vs Imperative**: WebFlux 선택 (높은 동시성 요구사항 및 비동기 처리 최적화)
- **Message Protocol Design**: 커스텀 JSON 프로토콜 (STOMP 대체, 단순성과 확장성 균형)
- **Database Strategy**: 폴리글랏 퍼시스턴스 (데이터 특성별 최적 데이터베이스 선택)
